## Обзор

Клиент держит у себя копию данных сервера и меняет их запросами.

- **Сервер → клиент: подписки.** Сразу после подключения сервер присылает все данные
  каждой модели, а дальше — только изменения. Клиенту не нужно ничего запрашивать,
  чтобы увидеть актуальное состояние: оно приходит само, в том числе когда данные
  изменил другой клиент или сам сервер (обновление подписок, проверка серверов).
- **Клиент → сервер: запросы.** Клиент просит изменить модель (`add`, `change`,
  `delete`) или выполнить действие (`request`). На каждый запрос приходит ровно один
  ответ — успех или ошибка.

Данные в ответах минимальны: результат изменения клиент видит в подписках, которые
приходят **до** ответа (см. [Порядок сообщений](#порядок-сообщений)). Поэтому, получив
успешный ответ, клиент уже имеет актуальные данные.

## Транспорт

WebSocket по адресу:

```text
ws://<XPR_UI_HOST>:<XPR_UI_PORT>/ws
```

Адрес и порт задают переменные окружения при запуске сервера (`README.md`): порт
обязателен, адрес по умолчанию `0.0.0.0`. Десктопное приложение слушает только
локальный адрес, например `ws://127.0.0.1:20800/ws`. TLS и авторизации нет.
На том же порту по HTTP раздаётся веб-интерфейс (`http://127.0.0.1:20800/`),
поэтому открытая оттуда страница подключается к `/ws` своего же адреса. Путь —
константа `WEBSOCKET_PATH` в `server/main.py`.

```js
const ws = new WebSocket("ws://127.0.0.1:20800/ws");
ws.onmessage = (event) => handle(JSON.parse(event.data));
ws.send(JSON.stringify({ type: "request", model: "refresh_subscriptions",
                         request_id: "1", payload: {} }));
```

- Одно WebSocket-соединение на клиента; клиентов может быть несколько одновременно.
- Каждое сообщение — один текстовый кадр с одним JSON-объектом.
- Бинарные кадры не принимаются: сервер закрывает соединение с кодом 1003.
- Сообщение больше 1 МиБ закрывает соединение с кодом 1009.
- Сервер шлёт ping раз в 30 секунд; браузер и библиотеки WebSocket отвечают
  на него сами. Клиент, который не ответил, отключается.
- Сжатие (`permessage-deflate`) сервер не принимает: кадры идут без него.
- Сервер пишет кадры в одно соединение строго в том порядке, в каком их отправил.
- При остановке сервер закрывает соединения с кодом 1001.
- При обрыве соединения неотправленные сообщения теряются. После переподключения
  клиент заново получает полный снимок всех моделей и должен заменить им свою копию.
  Переподключаться клиент решает сам, например с нарастающей паузой.

### Проверка Origin

Браузер позволяет любой открытой странице подключиться к `ws://127.0.0.1` и
указывает её адрес в заголовке `Origin`. Чтобы чужой сайт не мог управлять прокси,
сервер принимает соединение, только если:

- заголовка `Origin` нет — клиент не браузер: main-процесс Electron, скрипты, `aiohttp`,
  библиотека `ws` в Node.js;
- `Origin` — страница `http://` или `https://` на `localhost`, `127.0.0.1` или `[::1]`
  с любым портом, например dev-сервер веб-интерфейса `http://localhost:5173`;
- `Origin` явно разрешён в `WEBSOCKET_ALLOWED_ORIGINS` в `server/main.py`, например
  `app://x-proxy-router` для собственного протокола Electron;
- сервер слушает адрес, доступный из сети (`XPR_UI_HOST` — не loopback, например
  `0.0.0.0`), а `Origin` совпадает с заголовком `Host` запроса: это страница самого
  сервера, открытая по его адресу, например `http://192.168.1.2:20800`. На локальном
  адресе такие страницы не принимаются: иначе чужой сайт, имя которого указывает на
  `127.0.0.1` (DNS rebinding), выглядел бы как свой.

Иначе рукопожатие отклоняется с HTTP 403. Страницы, открытые из файла (`file://`)
или в песочнице (`Origin: null`), не принимаются: в Electron подключайтесь из
main-процесса или загружайте интерфейс через разрешённый адрес.

## Виды сообщений

У каждого сообщения есть поля `type` и `model`.

| Направление | `type` | Назначение |
| --- | --- | --- |
| сервер → клиент | `subscription` | данные модели: снимок или изменения |
| сервер → клиент | `response` | ответ на запрос клиента |
| клиент → сервер | `add`, `change`, `delete` | изменить модель |
| клиент → сервер | `request` | выполнить действие |

## Подписки на модели

### Формат

```json
{
  "type": "subscription",
  "model": "outbound_server",
  "refresh": false,
  "payload": [ { "id": "a54133ec974a", "name": "NL", "...": "..." } ],
  "deleted_ids": ["9f2c61d0b7e4"]
}
```

| Поле | Тип | Смысл |
| --- | --- | --- |
| `model` | string | имя модели: `server_settings`, `subscription_link`, `reg_filter`, `outbound_test`, `outbound_server`, `inbound_server`, `routing_rule`, `task` |
| `refresh` | boolean | `true` — полный снимок, `false` — изменения |
| `payload` | array | объекты модели **целиком**, со всеми полями |
| `deleted_ids` | array | `id` удалённых объектов; в снимке всегда пустой |

Каждая модель — коллекция объектов с уникальным `id`. Объект в `payload` всегда полный:
частичных объектов протокол не присылает.

### Снимок при подключении

Сразу после подключения сервер присылает по одному сообщению с `refresh: true`
на каждую модель, в таком порядке:

1. `server_settings`
2. `subscription_link`
3. `reg_filter`
4. `outbound_test`
5. `outbound_server`
6. `inbound_server`
7. `routing_rule`
8. `task`

Клиент **заменяет** коллекцию модели содержимым `payload`: объекты, которых нет
в снимке, удаляются. Так после переподключения исчезают объекты, удалённые, пока
клиент был отключён. Изменения, пришедшие после снимка, относятся к состоянию снимка.

### Изменения

Сообщение с `refresh: false` содержит только то, что изменилось с прошлого сообщения
этой модели:

- в `payload` — новые и изменённые объекты, каждый целиком;
- в `deleted_ids` — удалённые объекты.

Если данные записаны, но ни одно поле, видимое клиенту, не поменялось, сообщения нет.
Один `id` не попадает в одном сообщении и в `payload`, и в `deleted_ids`.

Как применять:

```js
function apply(collections, message) {
  const items = collections[message.model];      // Map id -> объект
  if (message.refresh) items.clear();
  for (const id of message.deleted_ids) items.delete(id);
  for (const item of message.payload) items.set(item.id, item);
}
```

### Когда приходят изменения

- После запроса любого клиента, который изменил данные, — всем подключённым клиентам,
  включая автора запроса.
- По инициативе сервера, без запросов:
  - обновление подписок при запуске сервера и каждые `subscription_refresh_interval`
    секунд (`outbound_server`, `server_settings`, `task`);
  - проверка серверов раз в час (`outbound_server`, `task`);
  - снятие `is_connected`, если подключённый сервер больше нельзя использовать
    (`outbound_server`);
  - запуск inbound при старте сервера: заполняется или очищается `error`
    (`inbound_server`);
  - смена подключения в режиме [автоподключения](#автоподключение) после проверки
    серверов, обновления подписок и при запуске сервера (`outbound_server`).

### Порядок сообщений

- Сообщения одного соединения приходят в порядке отправки.
- Изменения, вызванные запросом, приходят этому клиенту **до** ответа на запрос.
- Снимок и следующие за ним изменения согласованы: изменение не может прийти раньше
  снимка или потеряться между снимком и первым изменением.
- Порядок между разными моделями определяется порядком изменений на сервере.
  Например, при обновлении подписок: `task` (`running`), `outbound_server`,
  `server_settings`, `task` (`stopped`).

## Модели

Клиент получает только поля, которые можно показывать: секреты (адреса подписок,
UUID, пароли, ключи авторизации, сырые настройки провайдера) сервер клиентам
не отправляет никогда. Поля, которые клиент может изменить, перечислены
в [справочнике запросов](#справочник-запросов); остальные ведёт сервер.

### server_settings

Настройки всего сервера. Коллекция всегда из одного объекта с `id: 0`, он не удаляется.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | integer | всегда `0` |
| `subscription_refresh_interval` | integer | интервал автоматического обновления подписок в секундах, больше 0; по умолчанию 86400 (сутки). Отсчёт идёт от запуска сервера или от последнего изменения интервала; обновления по запросам расписание не сдвигают |
| `last_subscription_refresh` | string \| null | время последнего успешного обновления подписок ([формат](#время)); `null`, пока обновления не было. Ведёт сервер |
| `auto_connect` | boolean | режим [автоподключения](#автоподключение): сервер сам выбирает, к какому серверу подключаться, и меняет его, когда соединение стало плохим. По умолчанию `false`. Выключается, когда клиент сам выбирает сервер (`connect_outbound_server`) и когда подключённый сервер попадает под фильтр по имени |

```json
{
  "id": 0,
  "subscription_refresh_interval": 86400,
  "last_subscription_refresh": "2026-09-27T12:00:00Z",
  "auto_connect": false
}
```

### subscription_link

Ссылки на подписки провайдеров. Полный адрес ссылки секретный и клиентам
не отправляется, даже тому, кто её добавил. Ссылку можно добавить и удалить,
изменить нельзя: её удаляют и добавляют новую.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | UUID, выдаёт сервер при добавлении |
| `url_short` | string | схема и хост ссылки без логина, пароля, порта, пути и параметров |

```json
{ "id": "dbb5c053-1611-4bfe-b81c-a5ed2973a2a1", "url_short": "https://sub.example.com" }
```

Например, для `https://user:token@Sub.Example.com:8443/path?x=1` клиент увидит
`https://sub.example.com`.

### reg_filter

Фильтры серверов по имени. Сервер, имя которого подходит хотя бы под один фильтр,
получает `filtered: "by_reg_filter"` (см. [фильтрацию](#фильтрация)).

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | UUID, выдаёт сервер при добавлении |
| `reg` | string | непустой [шаблон](#шаблоны), уникальный среди фильтров |

`reg` — [шаблон](#шаблоны), который сравнивается со всем именем сервера (`name`) без
учёта регистра: `*RU*` находит `🇷🇺 RU Moscow` и `Peru`, `RU*` — только имена,
которые начинаются с `RU`, а `RU` — только имя `RU`. В шаблоне фильтра допустимы
любые символы, как в именах серверов. Проверять имена на клиенте не нужно:
результат приходит в поле `filtered` серверов.

```json
{ "id": "5f0e2b1c-7a47-4c1d-9a55-0c3f5b0d8e21", "reg": "*russia*" }
```

### outbound_test

Проверки, которые проходят серверы: при проверке сервера каждый `url` запрашивается
через него. Проверку можно добавить и удалить, изменить нельзя: её удаляют и
добавляют новую. По умолчанию проверок нет.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | UUID, выдаёт сервер при добавлении; ключ в `outbound_server.tests` |
| `url` | string | HTTP(S)-адрес, который запрашивается через проверяемый сервер; уникальный среди проверок |
| `rule` | string | какой HTTP-статус ответа считается успехом, см. таблицу ниже |

| `rule` | проверка пройдена, если статус |
| --- | --- |
| `status_204` | ровно 204 |
| `status_2xx` | 200–299 |
| `status_below_400` | меньше 400 |
| `status_below_500` | меньше 500 |
| `status_below_503` | меньше 503 |
| `any_status` | любой: сайт ответил |

Нет ответа (таймаут, ошибка соединения или TLS) — проверка не пройдена при любом правиле.
Редиректы не выполняются: статус 3xx и есть ответ.

Имени у проверки нет: клиент называет её по сайту из `url`, например `gstatic`
для `https://www.gstatic.com/generate_204`.

```json
{
  "id": "8d3f6a2e-4b1c-4f7a-9e05-2c6b8a1d7f34",
  "url": "https://www.gstatic.com/generate_204",
  "rule": "status_204"
}
```

### outbound_server

Серверы, загруженные из подписок. Набор меняется только при обновлении подписок.

**Идентификатор.** `id` — 12 шестнадцатеричных символов. Он сохраняется между
обновлениями, пока совпадают подписка, имя, тег, протокол, адрес и порт сервера.
Если провайдер поменял что-то из этого, сервер удаляется и появляется новый
с другим `id`. Остальные параметры (транспорт, TLS и т. п.) могут меняться при том же `id`.

**Поля подключения** — только для показа:

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | идентификатор сервера |
| `name` | string | имя от провайдера |
| `address` | string | домен или IP-адрес |
| `port` | integer | порт |
| `protocol` | string | `vless`, `shadowsocks`, `hysteria` |
| `subscription_id` | string \| null | `id` ссылки из `subscription_link`, откуда загружен сервер |
| `source_tag` | string \| null | тег от провайдера |
| `transport` | string | `tcp`, `grpc`, `ws`, `xhttp`, `hysteria` |
| `security` | string | `none`, `tls`, `reality` |
| `server_name` | string \| null | SNI |
| `fingerprint` | string \| null | TLS fingerprint |
| `alpn` | array of string | ALPN |
| `public_key`, `short_id`, `spider_x` | string \| null | параметры Reality |
| `allow_insecure` | boolean \| null | не проверять сертификат |
| `host`, `path` | string \| null | параметры WS/XHTTP |
| `service_name` | string \| null | параметр gRPC |
| `grpc_mode` | string \| null | `gun`, `multi`, `guna` |
| `xhttp_mode` | string \| null | `auto`, `packet-up`, `stream-up`, `stream-one` |
| `vless_flow` | string \| null | `""`, `xtls-rprx-vision`, `xtls-rprx-vision-udp443` |
| `shadowsocks_method` | string \| null | метод шифрования Shadowsocks, например `aes-128-gcm`, `2022-blake3-aes-256-gcm` |
| `shadowsocks_udp_over_tcp` | boolean \| null | UDP поверх TCP |
| `shadowsocks_uot_version` | integer \| null | версия UoT: 1 или 2 |
| `hysteria_version` | integer \| null | всегда 2 для Hysteria |

Поля с префиксом протокола (`vless_`, `shadowsocks_`, `hysteria_`) заполнены только
у серверов этого протокола; у остальных они `null`.

**Поля состояния** ведёт сервер:

| Поле | Тип | Смысл |
| --- | --- | --- |
| `ping` | integer \| null | лучшее время TCP-подключения к серверу, мс, не больше 500. `null` — не проверялся, не ответил или не TCP (Hysteria не пингуется) |
| `speed` | integer \| null | скорость загрузки через сервер, байт/с. `null` — не проверялся или не ответил на пинг; `0` — загрузка не удалась |
| `rating` | integer \| null | оценка 0–100, больше — лучше. `null` — не проверялся; `0` — недоступен или провалил все проверки |
| `tests` | object \| null | результаты проверок [`outbound_test`](#outbound_test): `id` проверки → `true`/`false`. `null` — не проверялся. После удаления проверки её ключ остаётся до следующей проверки сервера, а у добавленной ключа нет, пока сервер не проверят снова |
| `filtered` | string \| null | почему сервер отфильтрован: `by_reg_filter`, `by_ping`, `by_subscription`; `null` — не отфильтрован. См. [фильтрацию](#фильтрация) |
| `is_connected` | boolean | основной трафик ядра идёт через этот сервер; `true` не больше чем у одного сервера |

**Рейтинг.** Пинг даёт до 30 баллов (`1 − ping/500`), скорость до 30 (полный балл от
125 000 байт/с = 1 Мбит/с), доля пройденных тестов до 40. Непроверенные части не
учитываются, их вес делят остальные: серверы без пинга и настройки без тестов баллов
не теряют. Сервер, не ответивший на пинг, получает 0 и `filtered: "by_ping"`.

#### Фильтрация

Отфильтрованный сервер остаётся в коллекции, но к нему нельзя подключиться
(`conflict`), а проверки его пропускают. Показывать его или скрывать, решает клиент.
Подключённый сервер, отфильтрованный по имени, отключается (см. ниже).

| `filtered` | Когда | Проверяется | Когда снимается |
| --- | --- | --- | --- |
| `by_reg_filter` | имя подходит под один из [`reg_filter`](#reg_filter) | нет | после удаления всех фильтров, под которые подходит имя |
| `by_ping` | при последней проверке сервер не принял TCP-подключение за 500 мс (вместе с разрешением имени) | да, чтобы сервер мог вернуться | после проверки, в которой сервер ответил на пинг |
| `by_subscription` | зарезервировано, пока не приходит | — | — |

- Если причин несколько, приходит `by_reg_filter`. Когда подходящие фильтры
  удалены, снова видна `by_ping`, если она есть.
- Hysteria не пингуется и `by_ping` не получает.
- Фильтры действуют сразу: после `add` и `delete` для `reg_filter` и после
  обновления подписок серверы приходят клиенту уже с новым `filtered`.
- Подключённый сервер (`is_connected: true`), имя которого попало под фильтр,
  отключается в любом режиме: сервер блокирует основной трафик, снимает
  `is_connected` и выключает [`auto_connect`](#автоподключение). В итоге ничего
  не подключено, пока клиент не выберет сервер или снова не включит режим.
  Удаление фильтра подключение не возвращает.
- Подключённый сервер, получивший `by_ping` при проверке, остаётся подключённым:
  `by_ping` запрещает только новые подключения. В режиме

  работающий сервер, если такой есть.

#### Автоподключение

Когда в [`server_settings`](#server_settings) включён `auto_connect`, сервер сам
выбирает, к какому серверу подключаться. Он меняет сервер, когда соединение стало
плохим, но старается делать это редко.

Кроме полных проверок раз в час ([`test_outbound_servers`](#task)), сервер каждую
минуту быстро проверяет подключённый сервер: пинг и [`outbound_test`](#outbound_test),
без замера скорости. Если проверок нет, запрашивается
`https://www.gstatic.com/generate_204`. Результаты быстрых проверок клиентам не
приходят. Для выбора используется рейтинг, сглаженный по полным проверкам: один
удачный или неудачный замер сдвигает его только наполовину.

Подключённый сервер меняется по одной из трёх причин:

| Причина | Когда | Ограничения |
| --- | --- | --- |
| отказ | 3 быстрые проверки подряд не прошли (около 30 секунд) или сервер получил `by_ping` | нет |
| деградация | 2 быстрые проверки подряд оценили его на 20 и больше баллов ниже его обычного рейтинга | нужен сервер лучше быстрой оценки на 10 баллов; с прошлой смены прошло 15 минут |
| улучшение | два полных прохода проверки подряд другой сервер оценён выше на 10 баллов и больше | с прошлой смены прошёл час |

Быстрая проверка не прошла, если сервер не ответил на пинг или прошло меньше
половины тестов. Деградация и улучшение вместе дают не больше 4 смен за 24 часа.

- Выбираются только неотфильтрованные серверы с `rating` больше 0 по последней
  проверке: непроверенные (`null`) и не прошедшие проверку (`0`) не подключаются.
  Из серверов с равным рейтингом выбирается первый в порядке коллекции.
- Перед подключением сервер ещё раз быстро проверяется. Не прошёл — пробуется
  следующий, а этот 10 минут не выбирается. Пробуется не больше трёх серверов. Если
  не прошёл ни один, подключение не меняется: скорее всего, пропал интернет у
  самого роутера.
- Сервер, от которого ушли из-за отказа или деградации, 30 минут не выбирается.
  Каждый следующий такой уход за сутки удваивает срок, до 4 часов.
- Если ничего не подключено, лучший сервер подключается сразу, без ограничений:
  при запуске, после обновления подписок, в котором пропал подключённый сервер,
  и затем каждую минуту, пока не получится.
- Ошибки клиентам не приходят, они пишутся в лог сервера. Новое подключение приходит
  в `outbound_server`, как при `connect_outbound_server`.

Когда клиент включает режим, сервер выбирает сразу, до ответа. Если ничего не
подключено, подключается лучший сервер. Выбранный клиентом сервер остаётся, если
никакой другой не оценён выше него на 10 баллов и больше; сервер с `by_ping`
заменяется. `auto_connect: true` при уже включённом режиме ничего не меняет.

Обновление подписок может менять список серверов. У серверов, которые остались в
подписке, `id` сохраняется, и сервер помнит их историю. Пропавшие серверы
забываются, а новому серверу, чтобы заменить работающий, нужны два полных прохода
проверки. Пока подписки обновляются, быстрые проверки не идут.

Режим выключается:

- запросом `change` / `server_settings` с `auto_connect: false` — подключение
  остаётся прежним;
- когда клиент сам выбирает сервер запросом `connect_outbound_server`, в том числе
  пока сервер проверяет серверы для смены: выбор клиента остаётся;
- когда подключённый сервер попадает под фильтр по имени (`add` / `reg_filter`):
  сервер отключается, и ничего не подключено (см. [фильтрацию](#фильтрация)).

### inbound_server

Порты, на которых ядро принимает трафик пользователя. Трафик всех inbound идёт по
[правилам роутинга](#routing_rule), а не подошедший ни под одно — через подключённый
сервер (`is_connected` у `outbound_server`); пока ничего не подключено, такой трафик
блокируется. Проверки серверов идут через отдельный служебный порт ядра: его в
коллекции нет, и правила роутинга к нему не применяются.

При первом запуске сервер создаёт inbound по умолчанию: `proxy` на
`127.0.0.1:20808`. Его можно менять, выключать и удалять; удалённый, он не
появляется снова. Если удалить все inbound, трафик в ядро не принимается.

Одна модель на все типы inbound: поля с префиксом типа (`proxy_`) заполнены только
у inbound этого типа, у остальных они `null`. Сейчас тип один.

| `type` | Что это |
| --- | --- |
| `proxy` | SOCKS5 и HTTP-прокси на одном порту, UDP через SOCKS5 всегда включён |

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | UUID, выдаёт сервер при добавлении |
| `type` | string | тип inbound, см. таблицу выше; после добавления не меняется |
| `enabled` | boolean | `false` — inbound сохранён, но ядро его порт не слушает. По умолчанию `true` |
| `proxy_listen` | string | IP-адрес, на котором слушает прокси. По умолчанию `127.0.0.1` — только этот компьютер; `0.0.0.0` или `::` — все адреса, в том числе из локальной сети |
| `proxy_port` | integer | порт 1–65535; у разных inbound порты разные, даже у выключенных |
| `proxy_username` | string \| null | логин прокси; `null` — прокси без авторизации |
| `error` | string \| null | почему ядро не слушает порт, например `Port 1080 is already in use`. Ведёт сервер: заполняет, если включённый inbound не запустился при старте сервера, и очищает после успешного `change`. `null` — работает или выключен |

Пароль (`proxy_password`) секретный: клиентам он не отправляется, его можно только
задать в `add` и `change`. Логин и пароль задаются вместе: оба строки или оба `null`.
Адрес записывается в сокращённой форме: `::0` станет `::`.

```json
{
  "id": "3b0c8f2e-9d1a-4c55-8e0f-7a2d6c1b4e90",
  "type": "proxy",
  "enabled": true,
  "proxy_listen": "127.0.0.1",
  "proxy_port": 20808,
  "proxy_username": null,
  "error": null
}
```

### routing_rule

Правила роутинга: куда идёт трафик inbound к адресу. Правила проверяются по
возрастанию `priority`, и срабатывает первое подходящее. Трафик, не подошедший ни
под одно правило, идёт через подключённый сервер, как с `proxy`; это не настраивается.
По умолчанию правил нет.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | UUID, выдаёт сервер при добавлении |
| `priority` | integer | порядок проверки, 1 — первым. Номера правил всегда 1..N без пропусков: сервер сам сдвигает остальные правила при добавлении, перемещении и удалении |
| `reg` | string | [шаблон](#шаблоны) адреса назначения, уникальный среди правил; см. таблицу ниже |
| `action` | string | что делать с трафиком, см. таблицу ниже |

| `action` | Куда идёт трафик |
| --- | --- |
| `proxy` | через подключённый сервер; пока ничего не подключено, блокируется |
| `direct` | напрямую с этого компьютера, без сервера; работает и когда сервер не подключён |
| `block` | никуда: соединение сразу закрывается |

`reg` сравнивается с адресом назначения так, как его передало приложение, — с доменом
или с IP-адресом:

| Вид | Пример | Что можно |
| --- | --- | --- |
| домен | `youtube.com`, `*.youtube.com`, `*google*` | латинские буквы, цифры, `-`, `_`, `.`, `*` |
| IPv4 | `192.168.1.10`, `192.168.*`, `10.*` | точный адрес или первые целые октеты и `*` в конце |
| IPv6 | `::1` | только точный адрес |
| всё | `*` | любой домен и любой IP-адрес |

- Шаблон из цифр, точек и `*`, в котором есть цифра, — это IPv4. В нём `*` заменяет
  только целые октеты в конце: `192.16*`, `192.*.1.1`, `*.1` не принимаются.
- Доменный шаблон не подходит под IP-адрес, а IP-шаблон — под домен. Сервер не
  разрешает домены ради правил: `192.168.*` не сработает для `router.lan`, даже если
  тот разрешается в `192.168.1.1`. Исключение — имена из hosts-файла системы,
  например `localhost`: для правил они уже IP-адреса.
- Если приложение само разрешает DNS и передаёт в прокси IP-адрес, доменные правила
  для такого соединения не срабатывают.
- Чтобы охватить домен вместе с поддоменами, нужны два правила (`youtube.com` и
  `*.youtube.com`) или одно `*youtube.com`, которое захватит и `notyoutube.com`.
- Сервер хранит `reg` в нижнем регистре, `**` — как `*`, IPv6 — в сокращённой форме:
  `2001:DB8:0::1` станет `2001:db8::1`.
- Новые правила действуют на новые соединения; уже открытые соединения доживают
  по прежнему пути.

```json
[
  { "id": "6a1d1b0e-2f8c-4c39-a3a5-0b7f2a9e4d11", "priority": 1, "reg": "192.168.*", "action": "direct" },
  { "id": "c0e4a7d2-91b3-4f6e-8d25-3e7b1f0a6c58", "priority": 2, "reg": "*.youtube.com", "action": "proxy" },
  { "id": "f3b9e2c1-5a7d-4e08-b6c4-9d2a1e8f7b30", "priority": 3, "reg": "*", "action": "direct" }
]
```

### task

Долгие задачи сервера и их состояние. В коллекции есть все задачи, которые умеет
выполнять сервер, даже если сейчас они не идут; сортировка по `id`.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | имя задачи |
| `status` | string | `running` — выполняется, `stopped` — не выполняется |

| `id` | Что делает | Как запускается |
| --- | --- | --- |
| `refresh_subscriptions` | загружает все подписки и заменяет серверы | при запуске сервера, каждые `subscription_refresh_interval` секунд, после `add` / `subscription_link`, запросом `refresh_subscriptions` |
| `test_outbound_servers` | по очереди проверяет все серверы | раз в час (первый раз — через час после запуска), запросом `test_outbound_servers` |

Правила задач:

- Каждая задача выполняется не больше чем в одном экземпляре. Повторный запуск
  не начинает новую, а ждёт идущую.
- `refresh_subscriptions` при старте останавливает идущую `test_outbound_servers`.
- `test_outbound_servers` не запускается, пока идёт `refresh_subscriptions`.

`running` приходит при старте задачи, `stopped` — при завершении, чем бы она ни
закончилась: успехом, ошибкой или остановкой.

```json
[
  { "id": "refresh_subscriptions", "status": "stopped" },
  { "id": "test_outbound_servers", "status": "running" }
]
```

## Запросы

### Формат

```json
{
  "type": "change",
  "model": "routing_rule",
  "request_id": "7",
  "payload": { "id": "6a1d1b0e-2f8c-4c39-a3a5-0b7f2a9e4d11", "priority": 1 }
}
```

| Поле | Тип | Смысл |
| --- | --- | --- |
| `type` | string | `add`, `change`, `delete` или `request` |
| `model` | string | модель, которую меняют, или имя действия |
| `request_id` | string | непустая строка, которую выбирает клиент; возвращается в ответе |
| `payload` | object | данные запроса; для запросов без данных — `{}` |

Все четыре поля обязательны. Сервер не проверяет уникальность `request_id`: клиенту
стоит делать его уникальным в пределах соединения, иначе ответы не сопоставить.

### Два вида запросов

- **Изменение модели.** `type` — `add`, `change` или `delete`, `model` — имя модели.
- **Действие.** `type` всегда `request`, а само действие записано в `model`, например
  `refresh_subscriptions`. Новые действия добавляются только так, новых значений
  `type` не появляется.

### Правила разбора payload

- Неизвестные поля — ошибка `bad_request`, а не игнорирование. В том числе поля,
  которые ведёт сервер (`url_short`, `last_subscription_refresh`, `ping` и т. п.).
- `id` новых объектов выдаёт сервер; передать свой `id` в `add` нельзя.
- В `change` передаются `id` и только изменяемые поля; пропущенные сохраняют значения.
- Типы строгие: вместо целого нельзя передать строку, `true`/`false` не считаются числами.
- Пакетных запросов нет: один запрос — одно действие.

### Выполнение

- Запросы выполняются параллельно: долгий запрос не задерживает остальные, поэтому
  ответы могут прийти не в том порядке, в каком отправлены запросы. Сопоставляйте
  по `request_id`.
- Если клиент отключился, начатый запрос всё равно выполняется до конца, но ответ
  не отправляется. Долгие задачи (обновление подписок, проверка серверов) от отключения
  клиента не прерываются.

## Ответы и ошибки

### Успешный ответ

```json
{
  "type": "response",
  "model": "routing_rule",
  "request_id": "7",
  "ok": true,
  "payload": {}
}
```

`model` и `request_id` повторяют запрос. `payload` — результат, у большинства
запросов `{}`.

### Ответ с ошибкой

```json
{
  "type": "response",
  "model": "routing_rule",
  "request_id": "7",
  "ok": false,
  "payload": {},
  "error": {
    "code": "not_found",
    "message": "Routing rule not found",
    "details": { "field": "id" }
  }
}
```

| Поле | Смысл |
| --- | --- |
| `error.code` | машинный код ошибки; на него и стоит опираться |
| `error.message` | текст на английском для логов и отладки; может меняться, показывать его пользователю как есть не рекомендуется |
| `error.details` | дополнительные данные, всегда объект; часто `{}` |

Если сообщение не удалось разобрать, `model` и `request_id` в ответе равны `null`,
когда их не удалось прочитать; корректные значения возвращаются, даже если остальная
часть сообщения ошибочна.

Ошибка означает, что запрос ничего не изменил. Исключения:

- `add` / `subscription_link` с `subscription_error` — ссылка всё же добавлена;
- `cancelled` — отменённая задача могла успеть сделать часть работы;
- `internal_error` — изменения могли примениться частично.

Во всех случаях фактическое состояние приходит в подписках, поэтому клиенту
не нужно гадать, что изменилось.

### Коды ошибок

| `code` | Когда | `details` |
| --- | --- | --- |
| `bad_request` | не JSON-объект; `request_id`, `type` или `model` не непустая строка; `payload` не объект; нет обязательного поля, есть неизвестное или у поля неверный тип | `{field}` — имя поля; для ошибок самого сообщения — `{}` |
| `unknown_request` | нет запроса с такой парой `type` + `model`, например `change` для `subscription_link` | `{}` |
| `validation_error` | значение неверно по смыслу: URL не HTTP(S), интервал ≤ 0, неизвестное правило проверки, пустой или неверный шаблон, `priority` вне допустимых | `{field}`, если поле известно, иначе `{}` |
| `not_found` | объекта с таким `id` нет | `{field: "id"}` |
| `conflict` | противоречит текущему состоянию: URL подписки или проверки, фильтр или правило роутинга с таким шаблоном уже добавлены; проверка серверов во время обновления подписок; подключение к отфильтрованному серверу; порт inbound занят | см. справочник |
| `subscription_error` | подписки не загрузились; серверы остались прежними | `{failed_id}` — `id` ссылки, которая не загрузилась; у `add` ещё `{id}` новой ссылки |
| `core_error` | ядро прокси не выполнило действие; причина только в логе сервера | `{id}` сервера, inbound или правила роутинга |
| `cancelled` | долгую задачу, которой ждал запрос, остановила другая задача или остановка сервера | `{}` |
| `internal_error` | непредвиденная ошибка сервера; текст ошибки клиенту не отправляется | `{}` |

### add / subscription_link

Добавляет ссылку на подписку и загружает серверы всех подписок.

- **payload:** `{"url": "https://provider.example/sub/token"}` — HTTP(S)-адрес
  с хостом. Адрес секретный: в ответах и подписках его нет, только `url_short`.
- **Ответ:** `{"id": "<uuid новой ссылки>"}` — после загрузки серверов.
- **До ответа приходят:** `subscription_link` с новой ссылкой; затем, как при
  `refresh_subscriptions`: `task` (`running`), `outbound_server` (если серверы
  изменились), `server_settings` (новое `last_subscription_refresh`), `task` (`stopped`).
- Если обновление подписок уже идёт, сервер сначала дожидается его (оно началось
  до добавления ссылки), а затем запускает новое, поэтому серверы новой ссылки
  загружаются всегда.

| Ошибка | Когда | Изменения |
| --- | --- | --- |
| `bad_request` `{field}` | нет `url`, `url` не строка или есть лишнее поле (в том числе `id`); `field` — имя поля | нет |
| `validation_error` | URL не HTTP(S) или без хоста | нет |
| `conflict` `{field: "url"}` | такая ссылка уже добавлена | нет |
| `subscription_error` `{id, failed_id}` | ссылка сохранена, но какая-то подписка не загрузилась | ссылка **добавлена** и пришла в `subscription_link`; серверы прежние |
| `cancelled` | обновление остановлено остановкой сервера | ссылка добавлена |

### add / inbound_server

Добавляет inbound. Включённый inbound ядро начинает слушать до ответа: если порт
занят или адреса нет на компьютере, inbound не сохраняется.

- **payload:** `{"type": "proxy", "proxy_port": 1080}`; необязательные поля —
  `enabled`, `proxy_listen`, `proxy_username`, `proxy_password`
  ([модель](#inbound_server)). Логин и пароль передаются вместе или не передаются.
- **Ответ:** `{"id": "<uuid нового inbound>"}`, когда ядро уже слушает порт.
- **До ответа приходит:** `inbound_server` с новым inbound (без пароля).

| Ошибка | Когда | Изменения |
| --- | --- | --- |
| `bad_request` `{field}` | нет `type`, неверный тип поля, лишнее поле (в том числе `id` и `error`) | нет |
| `validation_error` `{field}` | неизвестный `type` (`type`); нет порта или он вне 1–65535 (`proxy_port`); адрес не IP (`proxy_listen`); логин без пароля или пароль без логина, пустой логин или пароль, `:` в логине (`proxy_username`, `proxy_password`) | нет |
| `validation_error` `{field: "proxy_listen"}` | такого адреса нет на этом компьютере | нет |
| `conflict` `{field: "proxy_port"}` | порт у другого inbound, у служебного порта проверок ядра или занят другой программой; `message` называет причину, например `Port 1080 is already in use` | нет |
| `core_error` `{id}` | ядро не смогло запустить inbound по другой причине | нет |

### change / inbound_server

Меняет inbound. Пропущенные поля сохраняют значения, `type` не меняется: чтобы
сменить тип, inbound удаляют и добавляют новый.

- **payload:** `{"id": "<uuid>", "proxy_port": 1081}`; можно передать `enabled`,
  `proxy_listen`, `proxy_port`, `proxy_username`, `proxy_password`.
  - Пароль меняется одним `proxy_password`, логин остаётся прежним.
  - `"proxy_username": null, "proxy_password": null` снимают авторизацию.
  - `enabled: false` — ядро перестаёт слушать порт; `enabled: true` — начинает.
- Включённый inbound ядро перезапускает с новыми параметрами до ответа. Уже открытые
  соединения через inbound, параметры которого не изменились, не обрываются.
  Запрос с теми же значениями снова пробует запустить inbound с `error` — например,
  когда занявшая порт программа закрылась. Успешный `change` очищает `error`.
- **Ответ:** `{}`. До ответа приходит `inbound_server`, если изменилось видимое
  клиенту поле; смена одного пароля сообщения не присылает.

| Ошибка | Когда | Изменения |
| --- | --- | --- |
| `bad_request` `{field}` | нет `id`, неверный тип, лишнее поле (в том числе `type` и `error`) | нет |
| `not_found` `{field: "id"}` | inbound нет | нет |
| `validation_error` `{field}` | как у `add`; например, `"proxy_username": null` при сохранённом пароле | нет |
| `conflict` `{field: "proxy_port"}` | как у `add` | нет: ядро слушает прежний порт |
| `core_error` `{id}` | ядро не смогло запустить или остановить inbound | нет |

### delete / inbound_server

Удаляет inbound; ядро перестаёт слушать его порт до ответа. Удалить можно и последний
inbound, в том числе созданный по умолчанию.

- **payload:** `{"id": "<uuid>"}`.
- **Ответ:** `{}`. До ответа приходит `inbound_server` с `deleted_ids: ["<uuid>"]`.

| Ошибка | Когда |
| --- | --- |
| `bad_request` `{field}` | нет `id`, неверный тип, лишнее поле |
| `not_found` `{field: "id"}` | inbound нет |
| `core_error` `{id}` | ядро не смогло остановить inbound; inbound остаётся |

### add / routing_rule

Добавляет правило роутинга. Ядро применяет правила до ответа: если оно не смогло,
правило не сохраняется.

- **payload:** `{"reg": "*.youtube.com", "action": "proxy"}`; `priority` можно не
  передавать.
  - Без `priority` правило становится последним (N+1).
  - `priority` от 1 до N+1 ставит правило на это место; правила с этим и большим
    `priority` сдвигаются на 1 вниз.
- **Ответ:** `{"id": "<uuid нового правила>"}`.
- **До ответа приходит:** одно сообщение `routing_rule` с новым правилом и всеми
  правилами, у которых изменился `priority`.

| Ошибка | Когда |
| --- | --- |
| `bad_request` `{field}` | нет `reg` или `action`, неверный тип (например, `priority` строкой), лишнее поле (в том числе `id`) |
| `validation_error` `{field: "reg"}` | пустой шаблон или шаблон не по правилам [модели](#routing_rule); `message` называет причину, например `In an IP pattern * replaces whole octets at the end, e.g. 192.168.*` |
| `validation_error` `{field: "action"}` | неизвестное действие |
| `validation_error` `{field: "priority"}` | `priority` меньше 1 или больше N+1 |
| `conflict` `{field: "reg"}` | правило с таким шаблоном уже есть (с учётом регистра и `**`: `*.YouTube.com` и `*.youtube.com` — один шаблон) |
| `core_error` `{id}` | ядро не смогло применить правила; ничего не изменилось |

### change / routing_rule

Меняет правило. Пропущенные поля сохраняют значения.

- **payload:** `{"id": "<uuid>", "priority": 1}`; можно передать `priority`, `reg`,
  `action`.
  - `priority` от 1 до N переносит правило: правила между прежним и новым местом
    сдвигаются на 1 к прежнему месту.
- **Ответ:** `{}`. До ответа приходит `routing_rule` с правилом и правилами,
  у которых изменился `priority`. Запрос с теми же значениями ничего не меняет и
  сообщений не присылает.

| Ошибка | Когда |
| --- | --- |
| `bad_request` `{field}` | нет `id`, неверный тип, лишнее поле |
| `not_found` `{field: "id"}` | правила нет |
| `validation_error` `{field}` | как у `add`; `priority` больше N |
| `conflict` `{field: "reg"}` | такой шаблон у другого правила |
| `core_error` `{id}` | ядро не смогло применить правила; ничего не изменилось |

### delete / routing_rule

Удаляет правило; правила после него поднимаются на 1.

- **payload:** `{"id": "<uuid>"}`.
- **Ответ:** `{}`. До ответа приходит `routing_rule` с `deleted_ids: ["<uuid>"]` и
  правилами, у которых изменился `priority`.

| Ошибка | Когда |
| --- | --- |
| `bad_request` `{field}` | нет `id`, неверный тип, лишнее поле |
| `not_found` `{field: "id"}` | правила нет |
| `core_error` `{id}` | ядро не смогло применить правила; правило осталось |

### change / server_settings

Меняет настройки сервера.

- **payload:** `{"id": 0, "subscription_refresh_interval": 3600, "auto_connect": true}`.
  Обязателен только `id`, всегда `0`.
  - `subscription_refresh_interval` — целое число секунд больше 0. Новое значение
    перезапускает таймер: следующее автоматическое обновление — через этот интервал
    от момента изменения. То же значение и изменение только `auto_connect` таймер
    не трогают.
  - `auto_connect` — `true` или `false`. `true` включает
    [автоподключение](#автоподключение): сервер сразу выбирает сервер. `true` при
    включённом режиме ничего не меняет. `false` выключает режим, подключение
    остаётся прежним.
  - `last_subscription_refresh` передать нельзя: его ведёт сервер.
- **Ответ:** `{}`. До ответа приходит `server_settings`, если что-то изменилось.
  После включения `auto_connect` затем приходит `outbound_server` с новым
  подключением, если сервер сменился.

| Ошибка | Когда |
| --- | --- |
| `bad_request` `{field}` | нет `id`, неверный тип (например, `auto_connect` не `true`/`false`), лишнее поле (в том числе `outbound_tests`: проверки — отдельная модель [`outbound_test`](#outbound_test)) |
| `not_found` `{field: "id"}` | `id` не `0` |
| `validation_error` | интервал ≤ 0 |

### request / refresh_subscriptions

Загружает все подписки сейчас и заменяет ими серверы.

- **payload:** `{}`.
- **Ответ:** `{}` — после окончания обновления.
- **До ответа приходят:** `task` (`refresh_subscriptions`: `running`), `outbound_server`
  (если серверы изменились), `server_settings` (новое `last_subscription_refresh`),
  `task` (`stopped`).
- Если обновление уже идёт, новое не запускается: ответ приходит, когда закончится
  идущее, с его результатом.
- Идущая проверка серверов останавливается.
- Серверы, которые остались после обновления, сохраняют `id`, результаты проверок
  (в том числе `filtered: "by_ping"`) и `is_connected`. После обновления ядро снова
  подключается к серверу с `is_connected`; если это невозможно или сервер
  отфильтрован по имени, флаг снимается.
  В режиме [автоподключения](#автоподключение), если подключённый сервер пропал,
  затем подключается лучший сервер: `outbound_server` приходит до `task` (`stopped`).
- Новые серверы, имя которых подходит под фильтр, сразу приходят
  с `filtered: "by_reg_filter"`.

| Ошибка | Когда | Изменения |
| --- | --- | --- |
| `bad_request` `{field}` | в `payload` есть поле | нет |
| `subscription_error` `{failed_id}` | какая-то подписка не загрузилась | серверы и `last_subscription_refresh` прежние |
| `cancelled` | обновление остановлено остановкой сервера | серверы могли не обновиться |

### request / test_outbound_servers

Проверяет серверы сейчас, по одному. Отфильтрованные серверы пропускаются, кроме
`by_ping`: их проверяют, чтобы они могли вернуться (см. [фильтрацию](#фильтрация)).

- **payload:** `{}`.
- **Ответ:** `{}` — после проверки всех серверов.
- **До ответа приходят:** `task` (`test_outbound_servers`: `running`), затем по сообщению
  `outbound_server` после проверки каждого сервера — с новыми `ping`, `speed`, `rating`,
  `tests`, `filtered`. В режиме [автоподключения](#автоподключение) в конце
  прохода сервер может смениться (отказ, улучшение или ничего не было подключено):
  тогда приходит ещё `outbound_server`. Последним приходит `task` (`stopped`).
- Фильтр, добавленный во время прохода, действует на серверы, которые ещё не проверены.
- Если проверка уже идёт (например, по расписанию), новая не запускается: ответ
  приходит по окончании идущей.
- Проверка одного сервера занимает несколько секунд, весь проход — пропорционально
  числу серверов. Ошибка на одном сервере не прерывает проход: он остаётся с прежними
  результатами.

| Ошибка | Когда | Изменения |
| --- | --- | --- |
| `bad_request` `{field}` | в `payload` есть поле | нет |
| `conflict` `{}` | идёт обновление подписок | нет |
| `cancelled` | проход остановлен: началось обновление подписок или остановка сервера | результаты уже проверенных серверов сохранены |

### request / connect_outbound_server

Направляет основной трафик прокси через сервер. Запроса на отключение нет: клиент
только меняет подключение на другой сервер (отключает сервер только
[фильтр по имени](#фильтрация)). Выбор клиента выключает
[автоподключение](#автоподключение), иначе сервер сам переключился бы обратно.

- **payload:** `{"id": "<id сервера>"}`.
- **Ответ:** `{}` — после переключения ядра.
- **До ответа приходят:** `server_settings` с `auto_connect: false`, если режим был
  включён, затем `outbound_server` с `is_connected: true` у выбранного сервера
  и `false` у прежнего.
- При ошибке ничего не меняется: ни подключение, ни `auto_connect`.
- Подключение запоминается: оно восстанавливается после перезапуска сервера и после
  каждого обновления подписок. Если сервер пропал из подписок или ядро больше не может
  к нему подключиться, `is_connected` снимается, и клиенты получают `outbound_server`.
- К отфильтрованному серверу подключиться нельзя. Если под фильтр по имени попал
  уже подключённый сервер, он отключается, а с `by_ping` остаётся подключённым
  (см. [фильтрацию](#фильтрация)).

| Ошибка | Когда | Изменения |
| --- | --- | --- |
| `bad_request` `{field: "id"}` | нет `id`, не строка, лишнее поле | нет |
| `not_found` `{field: "id"}` | сервера нет | нет |
| `conflict` `{id}` | сервер отфильтрован (`filtered` не `null`) | прежнее подключение сохраняется |
| `core_error` `{id}` | ядро не смогло переключиться, например сервер не поддерживается ядром | прежнее подключение сохраняется |

## Типовые сценарии

### Подключение клиента

```text
клиент  ── WebSocket connect ──►  сервер
клиент  ◄── subscription server_settings   refresh=true
клиент  ◄── subscription subscription_link refresh=true
клиент  ◄── subscription reg_filter        refresh=true
клиент  ◄── subscription outbound_test     refresh=true
клиент  ◄── subscription outbound_server   refresh=true
клиент  ◄── subscription inbound_server    refresh=true
клиент  ◄── subscription routing_rule      refresh=true
клиент  ◄── subscription task              refresh=true
клиент  ◄── subscription ... refresh=false   (дальше — только изменения)
```

### Добавление подписки

```text
клиент  ── add subscription_link {url} (request_id "1") ──►
клиент  ◄── subscription subscription_link   [новая ссылка]
клиент  ◄── subscription task                [refresh_subscriptions: running]
клиент  ◄── subscription outbound_server     [новые серверы], deleted_ids [пропавшие]
клиент  ◄── subscription server_settings     [новое last_subscription_refresh]
клиент  ◄── subscription task                [refresh_subscriptions: stopped]
клиент  ◄── response "1" ok {id}
```

### Проверка серверов

```text
клиент  ── request test_outbound_servers (request_id "2") ──►
клиент  ◄── subscription task             [test_outbound_servers: running]
клиент  ◄── subscription outbound_server  [сервер 1 с ping, speed, rating, tests]
клиент  ◄── subscription outbound_server  [сервер 2 ...]
         ...
клиент  ◄── subscription task             [test_outbound_servers: stopped]
клиент  ◄── response "2" ok {}
```

Индикатор «идёт проверка» удобно строить по модели `task`, а не по ожиданию ответа:
проверка по расписанию тоже меняет статус задачи, но ответа на неё нет.

### Подключение к серверу

```text
клиент  ── request connect_outbound_server {id} (request_id "3") ──►
клиент  ◄── subscription outbound_server  [выбранный: is_connected true, прежний: false]
клиент  ◄── response "3" ok {}
```

### Автоподключение

```text
клиент  ── change server_settings {id: 0, auto_connect: true} (request_id "5") ──►
клиент  ◄── subscription server_settings  [auto_connect true]
клиент  ◄── subscription outbound_server  [выбранный сервером: is_connected true,
                                           прежний: false; если сервер сменился]
клиент  ◄── response "5" ok {}
клиент  ── request connect_outbound_server {id} (request_id "6") ──►
клиент  ◄── subscription server_settings  [auto_connect false]
клиент  ◄── subscription outbound_server  [выбранный: is_connected true, прежний: false]
клиент  ◄── response "6" ok {}
```

### Фильтр серверов

```text
клиент  ── add reg_filter {reg: "RU*"} (request_id "4") ──►
клиент  ◄── subscription reg_filter       [новый фильтр]
клиент  ◄── subscription outbound_server  [серверы RU…: filtered "by_reg_filter"]
клиент  ◄── response "4" ok {id}
```

Если под фильтр попал подключённый сервер:

```text
клиент  ── add reg_filter {reg: "NL*"} (request_id "7") ──►
клиент  ◄── subscription reg_filter       [новый фильтр]
клиент  ◄── subscription server_settings  [auto_connect false, если режим был включён]
клиент  ◄── subscription outbound_server  [серверы NL…: filtered "by_reg_filter";
                                           подключённый: is_connected false]
клиент  ◄── response "7" ok {id}
```

### Inbound

```text
клиент  ── add inbound_server {type: "proxy", proxy_port: 1080} (request_id "8") ──►
клиент  ◄── subscription inbound_server  [новый inbound]
клиент  ◄── response "8" ok {id}
клиент  ── change inbound_server {id, proxy_port: 1081} (request_id "9") ──►
клиент  ◄── response "9" error conflict {field: "proxy_port"}   (порт занят;
                                           ядро слушает прежний 1080)
```

### Роутинг

```text
клиент  ── add routing_rule {reg: "192.168.*", action: "direct"} (request_id "10") ──►
клиент  ◄── subscription routing_rule  [новое правило: priority N+1]
клиент  ◄── response "10" ok {id}
клиент  ── change routing_rule {id, priority: 1} (request_id "11") ──►
клиент  ◄── subscription routing_rule  [правило: priority 1; прежние 1..N: priority 2..N+1]
клиент  ◄── response "11" ok {}
```

## Типы данных

### Время

Строка ISO 8601 в UTC с суффиксом `Z`, например `"2026-09-27T12:00:00Z"`. Дробная часть
секунд может присутствовать: `"2026-09-27T12:00:00.123456Z"`.

### Идентификаторы

| Модель | `id` |
| --- | --- |
| `server_settings` | целое число `0` |
| `subscription_link` | строка UUID |
| `reg_filter` | строка UUID |
| `outbound_test` | строка UUID |
| `outbound_server` | строка из 12 шестнадцатеричных символов |
| `inbound_server` | строка UUID |
| `routing_rule` | строка UUID |
| `task` | имя задачи |

Все `id` выдаёт сервер. Клиент не должен разбирать их содержимое: только сравнивать
и передавать обратно.

### Перечисления

Значения перечислений — строки в нижнем регистре, кроме `shadowsocks_uot_version`
и `hysteria_version` (целые). Клиенту стоит быть готовым к новым значениям
и показывать их как есть.

### Шаблоны

Фильтры серверов (`reg_filter.reg`) и правила роутинга (`routing_rule.reg`)
записываются одинаковыми упрощёнными шаблонами, а не регулярными выражениями:

- `*` — любые символы, в том числе ни одного;
- все остальные символы означают сами себя, `.` — точка;
- регистр не учитывается;
- шаблон сравнивается со всей строкой, как имена файлов: `*.txt`, а не поиск подстроки.

| Шаблон | Подходит | Не подходит |
| --- | --- | --- |
| `*RU*` | `🇷🇺 RU Moscow`, `Peru` | `NL 1` |
| `RU*` | `RU 1`, `ru-msk` | `🇷🇺 RU Moscow` |
| `*.youtube.com` | `www.youtube.com`, `a.b.youtube.com` | `youtube.com` |
| `youtube.com` | `youtube.com`, `YouTube.com` | `www.youtube.com` |

Какие символы допустимы, зависит от модели: в фильтре — любые, в правиле роутинга —
только символы домена или IP-адреса (см. [routing_rule](#routing_rule)).

### null и отсутствующие поля

В подписках сервер присылает все поля объекта, в том числе со значением `null`:
поле не пропадает. `null` означает «нет значения» или «не проверялось», как описано
у каждой модели.
