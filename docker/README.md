# Docker: сервер VLESS и панель с паролем

Compose запускает приложение (Python, веб-клиент и Mihomo), Caddy и Tinyauth v5.
Рассчитан на Linux и `network_mode: host`. Панель слушает только `127.0.0.1:20800`,
Tinyauth — `127.0.0.1:20801`. Caddy проверяет авторизацию для всех URL панели,
включая `/ws`, и выдаёт HTTPS на **8443**. Порт **443/TCP** остаётся для VLESS REALITY.
Docker socket контейнерам не передаётся.

## Установка из этого исходного кода

1. Направьте два DNS-имени одного родительского домена на сервер, например
   `panel.example.com` и `auth.example.com`. Используйте реальные домены вместо
   примеров. Если есть AAAA-записи, IPv6 тоже должен вести на этот сервер.
2. Разрешите входящие **80/TCP** (выпуск и продление сертификатов), **8443/TCP**
   (панель и авторизация), **443/TCP** (VLESS). Порты 20800 и 20801 открывать не нужно.
   Убедитесь, что эти порты не заняты другим сервисом. Для доменов панели используйте
   прямые DNS-записи без CDN-проксирования, если CDN не поддерживает вашу схему.
3. Из корня репозитория:

   ```sh
   cp docker/.env.example docker/.env
   docker run --rm -it ghcr.io/tinyauthapp/tinyauth:v5 user create --interactive
   ```

   Задайте логин и пароль в интерактивном запросе Tinyauth. Выберите **без**
   `format for Docker`: в `.env` хеш защищён одинарными кавычками. Вставьте результат
   `username:$2…` в `TINYAUTH_USERS='…'`. Заполните `XPR_PANEL_DOMAIN`,
   `XPR_AUTH_DOMAIN` и абсолютный `XPR_DATA_DIR`. Не используйте примерный пароль.

   ```sh
   chmod 600 docker/.env
   docker compose -f docker/compose.yaml --env-file docker/.env up -d --build
   ```

   `--build` нужен для установки именно этих изменений: опубликованный `latest`
   не обновляется автоматически при редактировании исходников. Образ можно собрать
   для amd64 или arm64; бинарники Mihomo включены в репозиторий.
4. Откройте `https://panel.example.com:8443`. Вас перенаправит на
   `https://auth.example.com:8443`; после входа панель подключается к `/ws` того же
   origin и управляет сервером. `VITE_WS_URL` задавать не нужно.

Caddy хранит сертификаты в `caddy-data`, Tinyauth — сессии и данные в `tinyauth-data`.
Настройки приложения находятся в `XPR_DATA_DIR/settings.sqlite3`. Они содержат
приватные ключи VLESS: ограничьте доступ к каталогу и его резервным копиям.
Суффикс `Z` у bind mounts позволяет запуск на системах с SELinux.

## Настроить сервер выхода

1. В блоке **Final outbound** включите **Server mode · direct Internet exit**.
   Трафик всех inbound будет выходить в Интернет напрямую с этого сервера.
   Подписки и подключённый outbound не требуются; auto-connect отключается.
2. В **Inbounds → Add VLESS** задайте:
   - Listen IP: `0.0.0.0` для внешних IPv4-подключений;
   - Port: `443`;
   - Public IP or domain: реальный доступный адрес сервера без схемы и порта;
   - TLS camouflage domain: доступный с сервера TLS 1.3 сайт на порту 443,
     сертификат которого соответствует указанному SNI. Это адрес маскировки,
     а не адрес вашей панели или самого VLESS listener; иначе получится петля.
3. Нажмите **Add**, затем **Copy connection link**. Сохраните ссылку приватно:
   она предоставляет доступ к прокси. Приватный ключ REALITY в неё не входит.

Профиль фиксирован: VLESS / TCP / REALITY / `xtls-rprx-vision`, клиентский fingerprint
`chrome`. UUID, X25519-ключи и случайный short ID создаются программой и сохраняются
при редактировании адресов. Редактируемы только адрес прослушивания, порт,
публичный адрес и SNI. Чтобы отозвать ссылку, удалите inbound и создайте новый.

REALITY уменьшает характерные признаки прокси, но не гарантирует необнаружимость
или доступность в сетях РФ. Доступность IP, выбор сайта маскировки и поведение
сети остаются важны. Этот проект не проверяет пригодность SNI автоматически.

## Настроить клиент с двумя ступенями

1. На клиенте оставьте **Server mode** выключенным.
2. Добавьте обычные подписки/серверы первой ступени и подключите один из них,
   либо включите существующий auto-connect.
3. В **Final outbound** вставьте ссылку с вашего сервера и нажмите
   **Save final server**, затем **Enable final outbound**.

Маршрут: **клиент → выбранная первая ступень → ваш final-сервер → Интернет**.
Смена/авторотация первой ступени не меняет final-сервер. При недоступной ступени
нет автоматического прямого выхода. Отключение final outbound отдельным
переключателем возвращает обычные правила маршрутизации, сохраняя ссылку.
Её также можно импортировать в **Subscriptions** как обычный VLESS-сервер.

В серверном режиме и при включённом final outbound пользовательские routing rules
не применяются: иначе `Direct` мог бы обойти нужный выход. Проверки серверов
тестируют первую ступень отдельно; хороший результат теста не означает, что
final-сервер доступен. После переключения режима/выхода переподключите приложения:
уже открытые TCP/UDP-сессии могут сохранять предыдущий маршрут.

Под «всем трафиком» здесь понимается трафик настроенных inbound. Приложение
не включает системный TUN/VPN: приложения клиента должны использовать его
SOCKS5/HTTP inbound. Служебные загрузки подписок и проверки имеют собственную
существующую логику. DNS имени самого final-сервера может разрешаться локально;
для исключения этого используйте его IP в экспортируемом адресе.

## Обновление и диагностика

```sh
docker compose -f docker/compose.yaml --env-file docker/.env up -d --build
docker compose -f docker/compose.yaml --env-file docker/.env logs --tail=100
```

Для установки опубликованной версии вместо исходников используйте `pull`, затем
`up -d --no-build`. Публикацию выполняет workflow «Docker image»; этот запрос
не публикует новый образ в GHCR. Перед обновлением сохраняйте резервную копию БД.
Миграции добавляют поля и сохраняют прежние настройки; откат на старый код после
создания VLESS inbound требует совместимой резервной копии.

Если панель открылась, но WebSocket не работает, проверьте домен/порт:
`XPR_PUBLIC_ORIGIN` должен точно совпадать с адресом панели. Compose задаёт его
автоматически. После истечения сессии обновите страницу для повторного входа.
Проверка Tinyauth происходит при HTTP-запросе и установлении WebSocket: уже
открытое WebSocket-соединение не закрывается автоматически при logout/истечении cookie.

При собственном reverse proxy сохраните loopback-bind приложения, защитите
**и статику, и `/ws`** и явно задайте `XPR_PUBLIC_ORIGIN=https://ваш-домен:порт`.
Не открывайте порт приложения наружу в обход Tinyauth.

## Повторяемая проверка

```sh
uv run python -m unittest server.tests.test_vless_egress -v
docker build -f docker/Dockerfile -t x-proxy:vless-test .
uv run python scripts/test-docker-auth.py
```

Первый тест запускает настоящие Mihomo с локальным TLS-сайтом маскировки и проверяет
две VLESS REALITY ступени, их переключение и отсутствие обхода. Второй запускает
временные Docker-контейнеры на случайных localhost-портах, проверяет защиту статики
и WebSocket, вход, изменение настройки через WebSocket и выход, затем удаляет их.
Тест использует локальный сертификат Caddy; публичный ACME требует настоящих DNS/портов.
